# 05-扩展功能 · 扩展功能管理规则

> v1 上线后新需求的增量演进工作区。遵循 OpenSpec 方法论（proposal → delta → tasks → design → archive），**手动管理，不依赖 CLI**。
>
> 核心原则：**SAD 冻结 · DD 单一基线 · 变更独立成目录 · 归档先合并再搬移**。

---

## 〇、五维判定卡（人读这张，AI 读下面全文）

一屏看完「这个变更我能不能自己拍」。细节去对应节。

```
① 身份：谁提案、谁审 —— A级需求方确认 / B级 Tech Lead / C级自审        → 第五节
② 权限：delta 只能扩展 DD；PRD/SAD 只读；A级必须停下退回需求            → 第二、九节  ← 安全核心
③ 工具：手动管理不依赖 CLI；从 changes/_template/ 复制四件套            → 第三节
④ 记忆：变更期状态在 changes/<id>/；归档时合并回 DD 成为长期记忆         → 第七节
⑤ 责任：archive 只读作审计；F-编号是追溯锚点；WBS 勾选即验收凭证        → 第七、八节
```

**接力线**：AI 做确定性的部分（读基线、查影响面、生成四件套、按 tasks 实现）；
**判断和后果留给人**（影响级别拍板、Open Questions 确认、降档许可、归档放行）。

## 一、使用阈值（先判断该不该来这里）

### 琐事白名单（闭集 —— 只有这五类可以直接改，不立提案）

1. Bug 修复（恢复设计本意，不改变设计意图）
2. 错别字、格式、注释
3. 依赖版本升级（非破坏性，不改调用方式）
4. 纯配置调整（不改功能逻辑与默认行为）
5. 已有测试的补充（不新增被测行为）

> ⚠️ **白名单之外一律立提案。** 不要因为「这个改动很小、很明确，顺手做了吧」而跳过 ——
> **「看起来简单」是失控的起点，不是例外条件。** 白名单是闭集，不做类比扩展。

### 立提案后的定级

| 场景 | 级别 | 走哪条路 |
|---|---|---|
| 已有模块的参数 / 流程 / 内部实现调整 | C | 本目录，proposal + delta + tasks |
| 新增功能模块 / 系统能力 / 跨模块改动 | B | 本目录，四件套（含 design.md） |
| 改变架构边界 / 对外接口 / 交付期 | A | **退回 `01-需求分析`**，走完整 PRD 周期 |

**识别信号**：如果这个变更需要重写「现状还原（AS-IS）」，那它已经不是扩展功能，是下一个大版本 —— 回 `01-需求分析/01-定义需求提示词.md`，把现有系统当 AS-IS 重走全流程。

**拿不准时按高一档处理**（升档随时可以，降档要人拍板 —— 见第五节）。

## 二、DD 治理规则

| 规则 | 说明 |
|---|---|
| **SAD 冻结** | P0 阶段起冻结，不原地修改。击穿架构边界的变更退回 `02-方案设计` |
| **DD 单一基线** | `02-方案设计/02-系统详细设计说明书【DD（Detailed Design）】.md` 是唯一真相源 |
| **增量演进** | 变更在 `changes/<change-id>/` 独立管理，**不直接改 DD**；归档时才合并回 DD |
| **不允许无记录覆盖** | 任何对 DD 的修改都必须有对应的已归档变更目录可追溯 |
| **Feature 编号锚定** | DD 每个「原子级功能块」带 `F-<模块>-<三位序号>`，如 `F-订单-007` |
| **退役号不复用** | 删除的 Feature 保留编号并标记 REMOVED，编号永不复用 |

> **为什么不用 `{项目名}-DD-v1.1.md` 版本号叠加**：攒到 v1.5 时，「当前真实设计」失去单一答案 —— 要读 DD 主文档 + v1.1 + v1.2 + … 全部叠加才能算出来。人还能勉强拼，AI 一次性喂进去就是上下文污染。改用「基线 + 变更区」双目录，DD 永远是当前真相。

## 三、目录结构

```
05-扩展功能/
├── README.md                          # 本文件：管理规则
├── 01-扩展功能需求提示词/
│   └── README.md                      # 变更提案生成提示词（喂给 AI 用）
├── changes/                           # 进行中的变更
│   ├── _template/                     # 变更模板四件套
│   │   ├── proposal.md.template
│   │   ├── delta.md.template
│   │   ├── tasks.md.template
│   │   └── design.md.template
│   └── archive/                       # 已归档变更（只读，审计追踪）
│       └── YYYY-MM-DD-<change-id>/
└── (无 specs/ 目录 —— 合并目标是 02-方案设计/DD)
```

**为什么没有 `specs/`**：真相源只能有一个。你的 WBS 门禁写的是「PRD + SAD + **DD** 必须 100% 映射」，如果在这里再建一个 `specs/`，读设计时要拼两处，正是要避免的问题。delta 归档时直接合并进 DD。

### archive 语义声明（重要）

本目录的 `changes/archive/` 与 SRS 其他三个 archive **语义不同**，别混：

| 目录 | 语义 |
|---|---|
| `history/archive/` | 按月切流水（时间性存旧） |
| `eval/archive/` | 任务结束整块移入（时间性存旧） |
| `01-需求分析/竞品用/archive/` | 源图归档（时间性存旧） |
| **`05-扩展功能/changes/archive/`** | **状态迁移**：提案已生效 → 合并进基线 → 提案退场 |

## 四、Change ID 命名

kebab-case，动词开头，全局唯一：

- `add-` 新增功能：`add-task-priority`
- `update-` 修改已有行为：`update-order-state-machine`
- `remove-` 移除功能：`remove-alipay-f2f`
- `refactor-` 重构（不改行为）：`refactor-payment-adapter`

ID 冲突时追加 `-2`、`-3`。这样 `ls changes/` 一眼看出每个变更在干什么。

## 五、A/B/C 影响分级

按**影响半径**定审批层级（来自 CMMI 配置管理体系，比「小迭代 / 大扩展」可判定）：

| 级别 | 影响范围 | 审批 | 必需产物 |
|---|---|---|---|
| **A** | 系统级需求、对外接口、产品价格或交付期 | 需求方确认 | 退回 `01-需求分析`，可能回改 PRD |
| **B** | 模块间功能接口、跨模块成本或进度 | Tech Lead 审核 | proposal + delta + **design.md** + tasks |
| **C** | 模块内部的设计与分配 | 自审 | proposal + delta + tasks（design.md 视下方硬触发线而定） |

### 分级只调「审查密度」，不调「安全底线」

- **可交易的**：design.md 的详细程度、是否需要他人审、估时精度 —— 用审查时间换交付速度，C 级可以省。
- **不可交易的**：第九节门禁全部条款 + 下方 design.md 硬触发线。**任何级别照做，不因为「急」或「小」而豁免。**

### design.md 硬触发线（命中任一即强制写，A/B/C 无豁免）

**判据是「可逆性」，不是影响半径。** 以下几类不可逆、改一次十倍价，地基错了上层盖越多推倒重来越贵：

- [ ] **DB 表字段变更** —— 迁移脚本 + 历史数据处理 + 回滚方案必须先写清
- [ ] **接口定义变更** —— 会被别人依赖，改一次要通知所有调用方
- [ ] **数据结构 / schema 变更** —— 含消息体、配置结构、持久化格式
- [ ] **迁移路径** —— 任何需要「老数据怎么办」的变更

> 一个只动模块内部的 C 级变更，如果动的是 DB schema，照样要写 design.md ——
> 因为 Migration Plan 和回滚方案就在里面。**烂 schema 能通过所有「能不能跑」的检查，然后在生产里慢慢放血。**

**唯一例外**：纯内部、马上要推翻重写的临时结构，且确认不会被别人依赖、将来不需要迁移。

### design.md 软触发条件（B 级判断参考，可协商）

- 跨多个模块 / 服务，或引入新架构模式
- 新增外部依赖
- 安全 / 性能复杂度高
- 技术选型存在多个备选方案，需要记录取舍

### 升降档规则

- **升档随时可以**，无需批准。
- **降档必须由人明示**，AI 不得自作主张降档，也不得以「任务描述说很急」「看起来不复杂」为由降档。
- 命中硬触发线的，**任何人都不能降档到免写 design.md**。

## 六、Delta 格式规范

`changes/<change-id>/delta.md` 按 Feature 编号分三段。每个 Feature 沿用 DD 提示词的「输入 / 核心逻辑 / 预期产出」三段结构。

### 6.1 ADDED —— 新增 Feature，给新编号

```markdown
## ADDED Features

### F-订单-007: 任务优先级字段

在 `Order` 模型新增 `priority: int` 字段，取值 1-5，默认 3。

- **输入**：`F-订单-003` 订单状态机已实现；PRD 节点 3.2 优先级排序需求
- **核心逻辑**：字段校验（1-5 越界拒绝）+ 默认值回填历史数据 + 索引优化排序查询
- **预期产出**：
  - `station/models/order.py` 新增字段
  - `alembic/versions/xxxx_add_priority.py` 迁移脚本（含历史数据回填）
  - `station/schemas/order.py` DTO 扩展
```

### 6.2 MODIFIED —— 改已有 Feature

**必须整段粘贴修改后的完整内容。** 合并时是整段替换，你少粘的部分会永久消失。

正确做法：
1. 到 DD 里定位 `F-订单-003` 的完整段落
2. 从标题到「预期产出」全文复制过来
3. 在副本上修改
4. 标题编号必须与 DD 完全一致

```markdown
## MODIFIED Features

### F-订单-003: 订单状态机

[此处是从 DD 复制的完整原文，已按新需求修改]

状态流转：`PENDING` → `PRIORITY_QUEUE`（新增） → `PROCESSING` → `COMPLETED`

- **变更原因**：支持高优先级订单插队
- **输入**：`F-订单-007` 优先级字段
- **核心逻辑**：（完整逻辑，含原有的全部内容 + 新增的插队判定）
- **预期产出**：（完整清单）
```

> **常见错误**：用 MODIFIED 添加新关注点却没包含原文。如果你不是在显式改动已有 Feature 的行为，应该改用 ADDED 新增一条。

### 6.3 REMOVED —— 废弃 Feature

```markdown
## REMOVED Features

### F-支付-012: 支付宝当面付

- **Reason**：支付宝 F2F API 2.0 于 2026-07-31 停服
- **Migration**：已引导用户切换到 `F-支付-015` 微信支付；历史订单保留只读记录，不再支持退款操作
- **Deprecated Date**：2026-08-01
```

编号 `F-支付-012` 保留在 DD 的「已废弃 Features」章节，**永不复用**。

### 6.4 五项必查清单（兼升档触发器）

每个 delta 必须逐项过一遍（来自美团「后羿」系统从生产事故反推的五类高频遗漏）：

| # | 检查项 | 命中后果 |
|---|---|---|
| 1 | **接口定义变更**（API 路由 / 参数 / 返回值 / 状态码） | **强制 design.md** |
| 2 | **DB 表字段变更**（迁移脚本 / 索引 / 历史数据处理） | **强制 design.md** |
| 3 | **异步消息变更**（队列 / topic / **消息体结构**） | 消息体结构变更 → **强制 design.md** |
| 4 | **配置项变更**（环境变量 / 配置文件 / 默认值） | 记入 Impact；同步 `.cursorrules/开发环境配置.md` |
| 5 | **定时任务变更**（cron / celery beat / 调度频率） | 记入 Impact；注明是否影响存量任务 |

前三项命中即触发 design.md 硬触发线（见第五节），**与 A/B/C 级别无关**。

无变更的项在 `proposal.md` 的 Impact 章节显式写明「无 DB 变更」，不留空 —— 空着无法区分「没有」和「忘了查」。

## 七、Archive 流程（两步原子操作，顺序不可颠）

只搬移不合并，archive 就变成垃圾堆 —— 过半年没人知道当前真实设计是什么，得把归档全翻一遍拼。

### Step 1：合并回基线

**先做这一步。** 把 `changes/<id>/delta.md` 合并进 `02-方案设计/02-系统详细设计说明书【DD（Detailed Design）】.md`：

| Delta 段 | 合并动作 |
|---|---|
| `ADDED` | 追加到 DD 对应模块章节末尾 |
| `MODIFIED` | 按 `F-` 编号定位，**整段替换** |
| `REMOVED` | 从原位置删除，移入 DD 末尾「已废弃 Features」章节，保留编号 |

同步更新 `03-WBS/01-WBS-开发待办.md`：
- `changes/<id>/tasks.md` 的已完成项（`[x]`）标记到 WBS 对应 Work Package
- 新增 WP 追加到 WBS 对应一级节点下，保持编号连续

**合并后自检**：
- [ ] DD 里能搜到本次 delta 的所有 `F-` 编号
- [ ] 没有编号冲突（同一编号出现两次）
- [ ] MODIFIED 的段落没有丢失原有内容
- [ ] WBS 的 Checklist 与 tasks.md 一致

### Step 2：归档目录

合并完成且自检通过后，才执行：

```bash
mv changes/<change-id> changes/archive/$(date +%Y-%m-%d)-<change-id>
```

归档后该目录**只读**，作为审计追踪 —— 以后想知道「这个功能为什么加、当时怎么权衡的」，直接读归档里的 proposal 和 design。

### 归档后的收尾

- 从本文件第九节「当前活跃变更」表里移除该行
- 如果变更引入了新的共享依赖或环境要求，同步 `.cursorrules/开发环境配置.md`

## 八、WBS 回流

扩展功能**必须**产出 `tasks.md` 作为 WBS 增量。没有 Work Package，编码阶段「Work Package First」「未端到端验收不得打勾」整套门禁就失效了。

### tasks.md 格式（遵循 WBS 提示词的三级分解）

```markdown
## 1. 订单模块          ← 一级节点：必须来自 DD 已有模块划分，不得自创

### 1.1 数据层           ← 二级节点：按 DD 的实现边界或自然依赖拆

- [ ] 1.1.1 Order 模型新增 priority 字段 + 迁移脚本
  - **依赖**：无
  - **验收**：迁移可正向执行与回滚；历史数据 priority 默认为 3
  - **估时**：1h

- [ ] 1.1.2 优先级排序索引
  - **依赖**：1.1.1
  - **验收**：EXPLAIN 确认走索引；10w 数据排序查询 < 100ms
  - **估时**：1h
```

### 与 WBS 主文档的关系

- `tasks.md` 是**增量**，不重复已有 WP
- 一级节点必须来自 DD 已有模块，不得自创（与 WBS 提示词的动态三级拆解原则一致）
- 归档时同步回 `03-WBS/01-WBS-开发待办.md`

## 九、门禁检查点

与 `srs-dev-pipeline/SKILL.md` 的硬性门禁对齐：

| 检查点 | 要求 |
|---|---|
| **不回改上游设计** | delta 不得修改 PRD / SAD，只能扩展 DD；击穿架构则退回 `02-方案设计` |
| **资料不足即停** | 无法确定影响面时输出《设计缺失项（Need Clarification）》，禁止自行脑补 |
| **安全三防不可删减** | SQL 注入 / XSS / CSRF + 参数校验（Zod）+ 限流，扩展功能同样必须覆盖 |
| **敏感信息不入日志** | 新增日志点必须过滤密码 / Token / Cookie / 验证码 |
| **端到端验收才打勾** | `tasks.md` 的 `[x]` 只能在端到端验收通过后标记 |
| **Feature 编号可追溯** | delta 引用的每个 `F-` 编号必须在 DD 中已存在，或由本 delta 显式新增 |
| **技术栈用法核对** | 新引入的库 / API 用法必须经 Context7 或官方文档核对 |
| **不可逆变更强制设计审** | 命中 design.md 硬触发线（DB / 接口 / schema / 迁移）→ 必须写 design.md，任何级别无豁免 |
| **降档需人明示** | AI 不得自作主张降低影响级别或跳过 design.md；升档随时可以 |
| **如实回报** | tasks.md 的 `[x]`、合并自检的勾选，必须反映真实状态。测试失败就写失败，跳过的步骤要说明 |

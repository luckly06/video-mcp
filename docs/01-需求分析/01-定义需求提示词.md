# 定义需求（投喂 ai-prd-writer 的输入包）

> 用途：把「视频去重工位 station 要补齐哪些能力」收敛成一份需求分析，直接投喂 `生成prd用/ai-prd-writer` 生成 PRD。
> 本轮不做竞品调研——产品已在开发中（station 已跑通并端到端验证）。本文件是「已有 MVP → 下一版补齐」的迭代需求。
> 下游产物：`02-PRD.md`。**PRD 只引用本文件的结论，不重复展开 AS-IS / Gap / TO-BE。**

本文件核心是三段递进论证：**现状还原（AS-IS）→ 差距分析（Gap）→ 流程重组（TO-BE）**，最后收敛成交给 PRD 的结论。

---

## 0. 问题定义（一句话）

> 对 **做短视频矩阵分发的内容运营者** + 在 **同一条素材要投多个平台 / 多个账号、需规避平台重复检测** 的场景下 + 因为 **现有工具 station 只复现了 CRVideoMate 去重面板的一部分操作（画面微调、微旋转、帧率、码率、去水印、裂变），改画面特征的手段单一，去重强度不足、变体同质化** + 希望得到 **一套覆盖「画面 / 时序 / 叠加 / 音轨」四类去重手段的可编程去重工位，一条素材能批量产出 MD5 与视频特征充分互异、且观感不崩的多个变体**。

避免「三太」：
- 不太大——只做「去重」这一件事，不做通用视频剪辑（画中画、片头片尾等纯编辑功能明确排除）。
- 不太空——优化目标明确：增加改变视频特征的维度 + 提升变体间差异度。
- 不太泛——「更好」有标准：见第 4 节验收指标（MD5 全异、感知哈希距离、观感不崩、分辨率保持）。

## 1. 现状还原（AS-IS）

station（`video-uniqueness/station/`）已上线并端到端验证通过，是本次迭代的基线。

- **现有端到端流程**（Web 工位壳 + MCP 无状态 server + 四级 Hook）：
  1. 选素材（限 `assets/` 白名单目录）
  2. `probe_video` 探测（分辨率 / 时长 / 码率 / MD5）——**强制走链前置**
  3. `dedup_video` 去重 → 人工决策确认 → 三项自检（MD5 变 / 分辨率保持 / 时长一致）
  4. `batch_fission` 裂变：一素材生成 N 个随机参数变体
  5. 产物落 `output/`，审计流实时落盘

- **现在用的能力（station 8 个 MCP 工具）**：
  `list_assets` / `probe_video` / `dedup_video` / `batch_fission` / `list_watermark_templates` / `remove_watermark` / `get_job` / `delete_output`

- **`dedup_video` 现在真正做的去重操作**（读 `pipeline.py` 确认）：
  - 画面微调：亮度 / 对比度 / 饱和度随机（eq）
  - 锐化（unsharp）、降噪（hqdn3d，可选）
  - 微旋转 + 放大裁回原尺寸去黑边（rotate，极小角度）
  - 帧率在 24/25/30 中随机、码率倍率或定值
  - 元数据清除 + 随机 comment
  - 自检：md5_changed / resolution_kept / duration_close

- **参照物 CRVideoMate 去重面板实际提供的操作**（据两张面板截屏核实，操作面板共 9 个标签页 + 画面调整区）：
  去水印 / 加水印 / 裁剪 / 画中画 / 去头尾 / 加头尾 / 变速 / 文本 / 背景音；
  画面调整区：亮度 / 对比度 / 饱和度 / 锐化 / 降噪、宫格分屏、分辨率、旋转翻转（左右转90°/水平/垂直翻转/微旋转/黑边去除）、帧率、抽帧、动态缩放、码率（倍率/定值）。

- **证据**：`CRVideoMate/截屏/原始面板.png`、`操作面板导航栏.png`；`station/server/pipeline.py`;`station/shared/rules.json`。

## 2. 差距分析（Gap）

AS-IS 与「充分去重」之间的差距。**这是 PRD 核心问题的论证来源。**

| 环节 | 现状(AS-IS) | 期望 | 差距 | 差距根因 | 严重度 | 对去重价值 |
|---|---|---|---|---|---|---|
| 画面构图 | 仅微调色彩+微旋转 | 能改构图（裁剪/翻转/缩放） | 缺**裁剪**、缺**90°/水平/垂直翻转** | 只复现了画面调整区一部分 | 高 | 高（改画面结构，感知哈希变化大） |
| 时序特征 | 仅改帧率 | 能改时长与帧序列 | 缺**变速**、缺**去头尾/截取**、缺**抽帧** | 时序类操作完全未实现 | 高 | 高（时长/帧特征变化，去重最有效之一） |
| 叠加元素 | 仅能去水印 | 能加图片水印/文字叠加改画面 | 缺**加水印**（rules 列了但没实现）、缺**文本叠加** | 加水印是空壳 | 中 | 中（叠加改画面，但需控观感） |
| 音轨特征 | 不动音轨（仅转码） | 能改音轨/加BGM | 缺**背景音/BGM** | 音轨类未实现 | 中 | 中（平台也比对音频指纹） |
| 画面分割 | 无 | 宫格分屏/动态缩放 | 缺**宫格分屏**、缺**动态缩放（Ken Burns）** | 未实现 | 低 | 中（改画面，但较激进） |
| 变体差异度 | 随机参数，但维度少 | 多维随机，变体充分互异 | 维度少→变体同质、易被判同源 | 去重手段单一 | 高 | 高（矩阵分发核心诉求） |
| 去重强度自检 | 只查MD5变没变 | 查感知相似度是否够低 | 缺**感知哈希/相似度自检** | 只有MD5这种弱指标 | 中 | 高（MD5变≠平台判不同） |

- **最痛的 1-2 个差距**（PRD 核心问题）：
  1. **改变视频特征的维度太少**（只有画面色彩+微旋转+帧率+码率），缺时序类（变速/去头尾）和构图类（裁剪/翻转）这些去重最有效的手段 → 去重强度不足、变体同质。
  2. **自检指标太弱**——只验 MD5 是否变，而 MD5 变了平台仍可能靠感知哈希判为同源 → 缺「去重是否真有效」的可信度量。

- **为什么值得做**：矩阵分发是高频刚需（一条素材 × N 平台 × M 账号，日常大量重复）。变体不够「不同」直接导致限流/判重/封号，去重强度就是这个产品的核心价值。

- **AI / 自动化优势判断**：本质是「随机参数编排 + ffmpeg 滤镜链拼装 + 效果自检」的自动化，station 已用 MCP+Hook 把它做成可编程、可审计、带人工决策点的工位；补齐维度是在既有架构上扩滤镜链，优势成立。

## 3. 流程重组（TO-BE）

改造后 station 怎么运转。保持现有架构（Web 工位 + MCP 无状态 + 四级 Hook + 强制走链），**只扩去重能力维度**。

- **目标端到端流程**：
  1. 选素材 → `probe_video` 探测（不变）
  2. 去重时可选「去重强度档位」或「勾选启用哪些维度」：
     **画面类**（色彩微调 / 锐化降噪 / 裁剪 / 翻转 / 缩放）
     **时序类**（帧率 / 变速 / 去头尾截取 / 抽帧）
     **叠加类**（加水印 / 文字 / 去水印）
     **音轨类**（BGM / 音量微调）
  3. 每维度参数随机（受 seed 控制，保证裂变变体互异）
  4. 处理后自检升级：MD5 变 + **感知哈希距离达标** + 分辨率保持 + 时长在允许范围
  5. 人工决策交付 / 触发再生成（不变）
  6. `batch_fission` 裂变时多维随机，产出充分互异的 N 个变体

- **落到产品 / 代码里的那一段**（= 本期开发范围）：
  - `pipeline.py`：新增 裁剪 / 翻转 / 变速 / 去头尾 / 加水印 / 文本 / BGM / 抽帧 等滤镜链构造函数；`dedup_video` 支持维度开关与强度档
  - 自检：接入感知哈希（如 pHash / ffmpeg signature）距离度量
  - `rules.json`：新增工具的四级分级 + 走链 + 字段校验（新写工具仍走 probe 前置）
  - Web 工位：暴露维度勾选 / 强度档 UI
  - 新增或扩展的 MCP 工具（命名待 PRD 定）

- **人工确认点 / 不交给 AI 的决定**：
  - 是否交付 / 是否再生成变体（保留现有人工决策门）
  - 高破坏性维度（如大幅变速、激进裁剪）默认关闭，需人工开启
  - `delete_output` 仍硬阻断

- **相比 AS-IS 被消除 / 合并的环节**：
  - 不再需要「跳出 station 用 CRVideoMate GUI 手动补做裁剪/变速」——去重全流程在工位内闭环。

- **明确不做（排除项，非去重的纯编辑功能）**：
  画中画、加头尾（片头片尾/边框）、画中画背景虚化等——这些是视频编辑需求，与去重目标无关，本期不做。

## 4. 交给 PRD 的收敛结论

投喂 ai-prd-writer 时据此推导，不要重写上面三段。

- **核心问题**（来自 Gap 最痛项）：station 去重维度太少（缺时序类/构图类操作）导致去重强度不足、变体同质；且自检只验 MD5、无法证明「平台会判为不同」。

- **MVP 只验证什么**：
  在既有架构上，**先补去重价值最高的 4 类操作**——**裁剪、翻转、变速、去头尾截取**（构图类2 + 时序类2），并**升级自检为「MD5变 + 感知哈希距离达标」**。验证：一条素材裂变出的 N 个变体，两两感知哈希距离均超过设定阈值，且观感不崩、分辨率保持。

- **本期做 / 本期不做**：
  - **本期做**：裁剪、翻转（90°/水平/垂直）、变速（含最短时长保护）、去头尾截取、感知哈希自检；对应 MCP 工具/参数扩展 + rules 分级 + Web UI 勾选。
  - **本期不做**：加水印/文本/BGM/抽帧/宫格分屏/动态缩放（列入 backlog，二期按去重价值排期）；画中画/加头尾等纯编辑功能**永久排除**。

- **待确认项**（最多 3 个）：
  1. **感知哈希方案与阈值**——用 pHash 还是 ffmpeg 内置 signature 滤镜？「变体算充分不同」的距离阈值定多少？（需用真实素材实测标定，PRD 阶段确认）
  2. **去重强度档位设计**——是给「轻/中/重」三档预设，还是让用户逐维度勾选？（影响 Web UI 与工具参数结构）
  3. **变速/裁剪的破坏性上限**——变速倍率、裁剪比例的安全区间是多少（既有效去重又不毁观感）？需实测标定默认区间。

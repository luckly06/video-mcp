## 一，文档使用原则（最高优先级）

本项目的 UI 原型不是重新设计产品，而是把已经确认的产品设计和 UI 蓝图实现为可运行的高保真原型。

### 1. 文档优先级与职责

1. PRD：定义业务功能、用户流程和页面能力；
2. SAD：定义系统模块、系统边界和页面所属系统；
3. DD：定义页面职责、字段、状态、交互、接口和业务流程；
4. 已确认 UI 蓝图：定义当前端的信息架构、页面清单、Layout、Design Token、组件与端侧规范；
5. WBS：仅用于了解实现顺序，不得作为新增页面或功能的依据。

所有页面、菜单、按钮、字段、弹窗、抽屉、流程和状态都必须映射到 PRD、SAD、DD 与已确认 UI 蓝图。不得自行新增、删除、合并或改写业务能力。

### 2. 开发前置门禁

仅在以下条件全部满足时才能开始输出代码：

- 已完整阅读全部资源；
- 已建立 PRD → SAD → DD → UI 蓝图 → HTML 页面映射；
- UI 蓝图已经人工确认；
- 所有 P0 阻塞问题已经关闭；
- 当前端范围明确为：纯浏览器桌面 Web；禁止混入桌面客户端窗口控制、移动端底部 Tab 或系统手势。

如存在页面缺失、字段冲突、流程冲突、权限不清、状态不全、端侧边界不清或蓝图未确认，必须先输出《待确认问题列表》，不得生成代码。

### 3. 页面整合与实现原则

允许根据已确认蓝图，把 DD 中的页面合理实现为页面、弹窗、抽屉、侧栏、向导或分步流程，但必须保证：

- 不丢失业务能力；
- 不改变业务流程；
- 不改变系统边界；
- 每项实现都可追溯到 PRD、SAD、DD 和蓝图；
- 不引入其他端的导航、窗口或手势范式。

## UI 风格与技术规范

- **整体风格**：参考并高质量还原飞书 Web 版，保持极简、高效、专业和一致的信息层级。
- **组件规范**：优先使用 Tailwind CSS utility class，方便后续迁移到 Vue 3。
- **视觉趣味**：严禁使用任何系统 Emoji；需要生动表达时，使用 SVG 卡通形象或插画。
- **图标源**：参考 https://www.iconfont.cn，或使用 Heroicons / Lucide 等开源 SVG 图标库；同一项目不得混用多套风格。
- **端侧规范**：纯浏览器桌面 Web；禁止混入桌面客户端窗口控制、移动端底部 Tab 或系统手势。
- **导航基线**：顶部工作区 + 左侧一级导航 + 二级侧栏 + 主内容区 + 可选右侧辅助面板
- **输入基线**：鼠标与键盘优先，支持 hover、focus-visible、快捷键和高信息密度操作

## 四，工程结构规范

建议结构如下；若蓝图另有明确约定，以蓝图为准：

```text
prototype/
├─ index.html
├─ pages/
│  └─ [module]/
│     └─ [page-name].html
├─ components/
├─ assets/
│  ├─ icons/
│  ├─ illustrations/
│  └─ images/
├─ data/
│  └─ mock-data.js
├─ scripts/
│  ├─ app.js
│  └─ interactions.js
├─ styles/
│  └─ tokens.css
└─ README.md
```

要求：

- 文件和目录使用小写 kebab-case；
- 禁止把全部页面堆进一个超大 HTML；
- 公共组件不得在各页面复制出不一致版本；
- 样式 Token 集中管理；
- 外部资源失效时不得导致核心页面完全不可用；
- 如使用 CDN，README 必须说明依赖和离线限制。

## 五，Tailwind CSS 与组件规范

- 以 Tailwind utility class 为主要样式表达；
- 颜色、字号、圆角、阴影、间距和边框必须来自统一 Token；
- 禁止大量使用无规则任意值；
- 同类组件必须使用一致的 class 组合；
- 状态必须覆盖 hover、focus-visible、active、selected、disabled、loading 和 error；
- 不得用颜色作为唯一状态表达；
- 自定义 CSS 统一放入 `styles/tokens.css`；
- 图标按钮必须有 tooltip 或可访问名称；
- 表单控件必须有 label、校验、错误提示和提交状态。

## 六，交互与数据规范

- 所有主操作必须有即时、明确、可感知的反馈；
- 列表、表格和卡片必须实现文档要求的加载、空、错误、分页或加载更多状态；
- 删除、退出、覆盖等高风险操作必须遵循文档定义的确认流程；
- Mock 数据必须覆盖正常、空、边界、异常和无权限场景；
- 示例数据不得伪造真实个人信息、密钥或敏感业务数据；
- 页面刷新后的状态保留策略必须按蓝图执行；
- 所有弹窗、抽屉和浮层必须处理打开、关闭、焦点、遮罩和层级。

## 七，PC Web 网页端专项实现规则

- 端侧边界：纯浏览器桌面 Web；禁止混入桌面客户端窗口控制、移动端底部 Tab 或系统手势。
- 典型尺寸：1024×768、1280×800、1366×768、1440×900、1920×1080
- 导航模型：顶部工作区 + 左侧一级导航 + 二级侧栏 + 主内容区 + 可选右侧辅助面板
- 输入模型：鼠标与键盘优先，支持 hover、focus-visible、快捷键和高信息密度操作
- 禁止混入其他端的窗口、浏览器栏、系统栏、导航或手势；
- 任何端侧能力都必须有 PRD、SAD、DD 或已确认蓝图依据；
- 空间不足时优先保证任务完成路径，不得通过隐藏核心业务能力来“适配”。

## 八，Chrome DevTools MCP 验收流程（强制）

必须配合 `https://github.com/ChromeDevTools/chrome-devtools-mcp` 完成：

1. 启动原型并确认全部页面可访问；
2. 检查 Console、Network、DOM 和可访问性树；
3. 按典型用户 Flow 完成端到端操作；
4. 开 sub-agent 分别执行视觉、交互、响应式和可访问性 review；
5. 逐一切换并截图：1024×768、1280×800、1366×768、1440×900、1920×1080；
6. 检查溢出、截断、错位、遮挡、滚动、点击热区、焦点和弹层层级；
7. 检查加载、空、错误、无权限、禁用、超长文本和极端数据；
8. 清洗案例库截图，删除重复、失败和无代表性的图片；
9. 修复全部 P0 / P1 问题后重新截图复验；
10. 输出《Chrome DevTools MCP 验收报告》。

验收报告至少包含：

| 页面 / Flow | 视口 | 检查类型 | 问题 | 严重级别 | 修复结果 | 截图编号 |
|---|---|---|---|---|---|---|

## 九，可访问性要求

- 使用语义化 HTML；
- 所有可交互元素可通过键盘或本端等效输入操作；
- 图标按钮必须提供可访问名称；
- 表单控件必须关联 label；
- 焦点顺序符合视觉顺序；
- `focus-visible` 清晰可见；
- 文本与背景对比度满足 WCAG 2.1 AA；
- 动画尊重 `prefers-reduced-motion`；
- 状态变化不得只靠颜色表达；
- 弹窗打开后管理焦点，关闭后恢复焦点。
